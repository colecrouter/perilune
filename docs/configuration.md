# Configuration workspace

Open **Configuration** with an owner account. Configuration files can contain
credentials and private macros, so operators and viewers cannot read the file API,
backups, or exports. Files never enter the shared printer dashboard stream.

The first workspace supports existing UTF-8 cfg, conf, ini, yaml, yml, and json
files up to 256 KiB. Simulator files are examples stored in SQLite. Live mode
reads supported files from Moonraker's config root through the backend; private
Moonraker addresses and API keys are never returned to the browser.

## Explained settings and raw source

Explained settings provide context, units, and Klipper documentation for a small
set of scalar printer/extruder/probe settings. They describe the selected file,
not current runtime readings or the final result of included-file overrides.
Repeated sections/keys, multiline values, expressions, and unknown settings stay
in raw source. Local numeric input bounds are editing aids, not hardware validation.
Klipper must validate the complete configuration, includes, modules, and macros.

A guided edit replaces only the numeric source span. Raw source remains canonical;
comments, includes, Jinja macros, delimiter choice, and untouched line endings are
preserved. YAML/JSON files stay raw text rather than being converted to Klipper INI.
Includes are shown without flattening; wildcard expansion and override resolution
remain Klipper's responsibility.

Klipper's SAVE_CONFIG header and everything below it appear as an inspectable,
protected block. Saves compare the complete generated suffix against the opened
revision and reject changes to it. A malformed header or ordinary text below it
is explained rather than silently repaired. Add notes and directives above the
block. This protects file bytes; it does not replace Klipper's autosave parser.

## Source editor

Raw source uses an on-demand CodeMirror editor with line numbers, search/replace,
undo/redo, bracket matching, and VS Code keyboard shortcuts. Klipper config
highlighting distinguishes sections, options, comments, G-code, and template
expressions. YAML and JSON files use their native language modes. Highlighting
is descriptive; it does not validate firmware settings or run macros.

Hover a Klipper property name to highlight it and read its upstream explanation.
Help follows the local section and kinematics; comments, values, macro bodies,
and settings without matching documentation do not trigger it. Place the cursor
on a key and press Ctrl/⌘ Shift Space for keyboard help; Tab reaches its
documentation link and Escape returns to the editor. Reference availability
does not affect draft editing or undo history.

Use Ctrl/⌘ F to search and Escape to close search. Tab indents using four spaces;
Escape followed by Tab moves focus out of the editor. Existing tabs and formatting
are preserved. Editor text changes pass through the same source-preserving draft
flow; the generated calibration block stays outside the editable document.

Incoming state that leaves your draft unchanged keeps selection and undo history.
Replacing the source explicitly (such as loading a backup, discarding, or adding
an upstream option) starts a fresh undo history. Switching files or editor modes
keeps draft text but remounts the editor and starts a new history. If the enhanced
editor cannot load, plain text editing remains available.

## Upstream reference

**Klipper reference · Find or add a setting** browses upstream option explanations
for existing sections. Search names or descriptions, and choose a documentation
context when kinematics are supplied by another file. Different kinematics retain
their separate explanations. The revision and original source are linked; your
installed firmware may differ.

The catalogue is generated by a prerendered SvelteKit endpoint at build time from
a commit-pinned, checksum-verified Klipper Markdown source. A matching bundled
snapshot keeps builds working without upstream access. Production serves the
static catalogue; no printer data is included. Licensing and update instructions
live in `src/lib/server/reference/README.md`.

Options are marked as present locally, calibration-generated, or absent from this
file. Includes are not resolved. To add an option, explicitly enter a single-line
value and acknowledge checking included files when present. Reference examples
never prefill your chosen value or silently become defaults. Additions stay in the
draft until the normal review/export/save flow. Repeated or ambiguous sections,
generated values, and mismatched local kinematics cannot use this shortcut.
Multiline values and creating new sections remain raw-source operations.

## Drafts, review, and simulator saves

Each file keeps its own draft while switching files in this tab. Failed file
navigation, refresh errors, and changed saved revisions do not replace drafts.
Leaving the workspace or closing/reloading the tab prompts while drafts remain.
Drafts are not persisted in browser storage; export or save before leaving.

**Review changes…** compares the draft with its opened revision. The bounded
preview shows the changed region (up to 200 lines per side), including unchanged
lines between separated edits. For larger changes, inspect/export the full raw
source before confirming. **Save simulator file** writes only the example file;
it neither changes running printer state nor restarts anything.

A save checks the original revision and writes the previous source as a backup
in the same transaction. Concurrent edits produce a conflict with the draft intact.
**Check saved version** retrieves the current source; conflicting changes can be
inspected before loading the saved version and reapplying your draft manually.
There is no automatic conflict merge or forced overwrite.

The latest 20 backups per file are retained. **Load backup into draft…** lets you
review a previous version; saving it creates a new revision and another backup.
Retries with the same save ID return the original receipt without duplicate backups.

## Live scope

By default, live mode supports owner-only browsing, local draft editing, change
review and UTF-8 export. Live application is a separate, default-disabled opt-in
workflow described below. No SAVE_CONFIG command or deletion is issued. Unsaved runtime calibration changes may
not be represented by the file on disk. Coordinated live writing, include-aware
validation, configuration creation/renaming, and a reviewed calibration-proposal
application flow remain follow-ups.

References: [Moonraker file management](https://moonraker.readthedocs.io/en/latest/external_api/file_manager/),
[Klipper configuration reference](https://www.klipper3d.org/Config_Reference.html),
[Klipper config/autosave implementation](https://github.com/Klipper3d/klipper/blob/master/klippy/configfile.py).

## Reviewed application and recovery (opt-in)

`PERILUNE_LIVE_CONFIGURATION=true` enables one-file reviewed uploads and Klipper
restarts. Keep this off until coordinated testing with the owner. The initial
rollout requires exclusive printer use: other interfaces can edit files or send
commands outside Perilune's reservation, and Moonraker uploads do not provide
atomic compare-and-swap with external writers.

Review the diff, confirm the source changes, then separately confirm the restart.
There is no full Klipper/Jinja syntax validation or guarantee of hardware safety.
Pending SAVE_CONFIG changes, active printing/motion/calibration, and nonzero
nozzle/bed heater targets block admission. Python/Pyodide language tooling is not
required; richer browser validation/LSP is tracked in issue #33.

Before upload, SQLite stores the exact previous/proposed file and an operation
receipt. Only one operation is admitted, with no waiting queue; it expires after
30 seconds if not dispatched. The backend owns execution across navigation and
client disconnects. It rechecks owner authorization, printer readiness and saved
bytes immediately before writing, verifies uploaded bytes, and requests RESTART.
It never issues SAVE_CONFIG or FIRMWARE_RESTART. Existing generated suffix guards
apply to new drafts.

A successful HTTP save is not a verified startup. Perilune requires a positive
observed Klipper startup/disconnection transition followed by ready, and verifies
that disk bytes still match. Very fast/unobserved restarts, timeouts or lost
acknowledgements remain unknown. Commands are never automatically replayed.

Recovery is owner-only and remains visible even if opening a configuration file
fails. An attention banner links to it from other app pages. Startup diagnostics,
snapshots and operation state survive page and backend restarts. The latest 20
operations are retained; snapshots are bound to the configured printer connection.
**Export previous file** works without Moonraker access.

**Revert changes and restart** restores only the latest operation's previous file,
after checking current bytes still match the operation. It refuses external edits.
Unknown outcomes first require **Check saved bytes and printer state**, which reads
without uploading or restarting. Checks never turn an unverified restart into
verified success. A failed restore can be explicitly retried after its outcome is
checked; a successful restore cannot be reversed by clicking the button again.
If both snapshots differ from the current file, export and compare manually.
Recovery requires Perilune and its database; uploads/restarts also require Moonraker.

## Calibration proposals

An owner can use **Review in configuration** on an extrusion-distance result.
The proposal appears above the editor. Choose the file containing the numeric
`[extruder] rotation_distance` and confirm the repeated measurement and review of
other config sources/runtime overrides. **Add to this draft** verifies the old
value and splices only the proposed number. Comments, gearing, other edits and the
protected generated suffix stay intact. A changed value, repeated/multiline setting,
missing option, generated override, simulator/live mismatch or expired proposal
blocks the handoff rather than guessing a target. No settings are inserted.

The handoff stays in memory in the current tab for 30 minutes and clears on refresh
or account change. It does not save/apply automatically. The ordinary review,
export, conflict checks and opt-in application/recovery flow still apply. Z-offset
and mesh persistence remain in their existing dedicated calibration workflows.

## Finding files and macros

The file browser searches paths, groups folders and scrolls independently of the
editor. Klipper `SAVE_CONFIG` revisions named `name-YYYYMMDD_HHMMSS.cfg` are grouped
under an existing `name.cfg`, newest first. This convention follows [Klipper’s
save implementation](https://github.com/Klipper3d/klipper/blob/master/klippy/configfile.py).
It is a navigation aid, not a claim that a file is active. Revision files open
read-only; opening one does not restore it. Export or copy reviewed changes into
the current source, then use the normal diff and recovery workflow.

Files with no explained settings open directly in raw source. Explicit editor-mode
choices stay with each file instead of carrying to every file you open. Macro
headers in the current draft provide source shortcuts; choosing a shortcut moves
the cursor to the definition without executing or rewriting it. Includes, macro
bodies, comments, and the protected generated suffix retain their existing semantics.
